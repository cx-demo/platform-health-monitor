# PHMS architecture

## Purpose

The Platform Health & Mission Readiness Service (PHMS) exposes subsystem
telemetry for a mixed fleet through a single sustainment API. Maintenance
planning, sortie generation, availability reporting and the customer
sustainment portal all consume it.

## Layering

| Layer | Module | Responsibility |
|---|---|---|
| Transport | `src/main.py` | FastAPI routes, HTTP status codes, error shaping. Serves rev C at `/platforms` and mounts the rev D sub-application at `/v2`. No business rules. |
| Domain | `src/readiness_service.py` | Projection of the internal platform model onto the ICD payloads (`get_platform_summary` for rev C, `summarise_v2` for rev D) and the single readiness classifier `classify_readiness` (rule `SYS-4412-R1`). All classification logic belongs here. |
| Model | `src/models.py` | Pydantic v2 internal domain model. |
| Data | `src/repository.py` | Platform store. In-memory fixture in this build; a sustainment data source in production. |

The layering is enforced by review and by `.github/copilot-instructions.md`.
Route handlers must not contain business rules.

## Internal model vs. public payload

`src/models.py` carries more information than the API exposes. `mission_critical_fault`
and `telemetry_age_seconds` are internal diagnostics and are deliberately **not**
projected by `get_platform_summary`. Leaking fault codes or diagnostic detail
through the public API is a security and interface concern, not a convenience.
Both are optional: an absent value means "not reported" and is classified as
missing telemetry by rule `SYS-4412-R1`, never as fresh or fault-free.
The subsystem `operational` flag is optional in the same way. Fault and
operational flags that are not real booleans are held as not reported, never
coerced to `true` or `false`.

The projection functions are the single points at which internal state becomes
external contract: `get_platform_summary` for rev C on `/platforms`, and
`summarise_v2` for rev D on `/v2/platforms`. Readiness is published only on
`/v2`. Any change to either projection is an ICD-PHM-002 interface change.

## Interface control

`docs/icd/ICD-PHM-002.md` is the controlling document for the public payload.
`tests/contract/test_icd_phm_002_compatibility.py` asserts the rev C field set
exactly on both `/platforms` endpoints — additional undeclared fields fail the
contract suite, because at least one downstream consumer validates strictly.
`tests/contract/test_icd_phm_002_rev_d.py` asserts the rev D field set exactly
on both `/v2` endpoints and checks it against the ICD rev D platform record
table. When an ICD
revision changes the payload, `tests/contract/` is updated to it in the same
pull request, at least as strictly, with code-owner approval of both.

The OpenAPI documents generated by FastAPI are the machine-readable form of
the ICD and are expected to agree with it: `/openapi.json` (rev C, 2.3.0) and
`/v2/openapi.json` (rev D, 2.4.0).

## Fleet fixture

Three platforms, one per customer domain:

| Platform | Type | Domain reading |
|---|---|---|
| `LND-114` | `LAND` | Vehicle serviceability, powerpack/drivetrain health |
| `AIR-207` | `AIR` | Subsystem prognostics feeding dispatch decisions |
| `MSN-330` | `MISSION_SYSTEM` | Deployed mission system readiness rollup |

`MSN-330` deliberately carries a mission-critical fault, a 94 °C generator and a
stale comms telemetry age. None of that is visible through the current API —
which is precisely the problem SYS-4412 addresses.
